## 实施记录

### 关键决策

- **SQLite 驱动**：采用 Electron 43 内置 Node 24.18.0 的 `node:sqlite`（`DatabaseSync`，同步 API），避免原生模块与 esbuild bundle 冲突；已探测确认 WAL、外键、FTS5、`user_version`、`backup` 全部可用。
- **Worker 隔离**：同步 SQLite 放进 `worker_threads`，`worker_threads` 天然一次处理一条消息，写入自然串行化，网络事件循环不因存储 I/O 阻塞。Capture 与 Diagnostics 各用独立 Worker/连接/数据库。
- **构建/打包**：`proxy-core` esbuild 改多入口（`entry.cts` + `storage/storage-worker.cts` + `diagnostics/diagnostics-worker.cts`），用 `--outdir=dist --outbase=src --out-extension:.js=.cjs` 保持 `entry.cjs` 路径稳定；worker 由 `__dirname` 定位同级 `storage/`、`diagnostics/`。Forge `extraResource` 已递归复制整个 `dist/proxy-core`，无需改动。
- **数据目录**：Main `CoreRuntime.launchCoreProcess` 通过 `--data-dir=<userData>/storage` fork 参数注入 Core；`entry.cts` 据此构建 `StorageService` 与 `DiagnosticsWorkerHost`，缺省则以无存储模式运行（存储 command 返回 internal，日志退回内存 Ring Buffer）。
- **边界**：存储读写与查询全部经 `StorageService` 意图型方法，Renderer 只见 `StorageUsage` DTO；SQL、数据库文件与 Blob 路径不出 Core。存储初始化失败不影响 CoreProcess 存活（`running` 仍只代表 Event Loop 可调度）。

## 后续增强（2026-07-15：诊断日志全组件覆盖 + 面板接线）

M2 的 Diagnostics 基座（Ring Buffer + Worker 持久化）之上，按可观测性反馈完善日志质量与覆盖，并把 Diagnostics 面板接上真实数据（T10.4 只读展示部分提前落地）：

- **共享 `DiagnosticsRecorder` 接口**：`core-diagnostics.ts` 导出 `DiagnosticsRecorder`（`info/warn/error(phase, fields)`），`CoreDiagnostics` 唯一实现；Proxy/Storage 经 `attachDiagnostics` 在 `CoreApplication` 装配后注入。原则：Core 各组件都记 initialize/生命周期/action/error 关键节点，不刷模板 phase。
- **全组件关键节点**：RpcServer `rpc.connected`/`rpc.connection-failed`（+ 每命令 1 条 `command.completed` 含 outcome/duration/errorCode）；Application `core.started`/`core.stopping`/`storage.ready`/`diagnostics.ready`；Proxy `proxy.listening`(host:port)/`proxy.stopped`/`tls.reconfigured`/`tls.client-error`/`client.error` + exchange 只记异常（aborted/5xx/persist-failed）；Storage host `storage.worker-ready`/`worker-fatal`/`worker-error`/`worker-exit`。
- **削噪音**：RpcServer 每命令由 5 条 phase（received/validated/handler.started/response.sent/completed）精简为 1 条 `command.completed`；`CoreDiagnostics.action` 去 `action.started` 只留 completed；`diagnostics.recent`/`diagnostics.query` 静默不自记（防 Renderer 轮询自污染有界 ring）；正常 exchange 不记。
- **Diagnostics 面板接真实数据**：新增 `getRecentDiagnostics(limit)` 窄 API（`core:get-diagnostics` → `diagnostics.recent`，不带 traceId 拉全部最近 200 条）；`toRendererDiagnosticRecord` 补 `traceId`。Renderer 新增 `DiagnosticsProvider`（2s 轮询 context），`TraceList`/`TraceDetail`/`DiagnosticsStatusbar` 从假数据改为按 requestId 聚合的真实命令行 + action 时间线 + 真实 records/dropped；`data.ts` 改为纯聚合/格式化工具（`aggregateTraces`/`buildTimeline`/`selectTraceRecords`，按 sequence 升序）。轮询遇预期内 `disconnected`（Core 重连瞬间）静默返回空快照。
- **待后续（T10.4/T10.5）**：Level/Outcome 过滤、脱敏 JSONL 导出，以及 Main/Renderer 日志纳入诊断（见 [M10.md](M10.md) T10.4/T10.5）。

## 进入条件与记录规则

- T2.0 先于 T2.1 执行；它只更新 Renderer 基线，不改变 M1 已完成的 IPC/Trace 验收，也不提前实现 M2 数据能力。
- T2.1 在 T2.0 验收后开始；任何跨进程查询/事件集成必须遵守 M1 已完成的协议边界。
- 捕获数据和 body 不进入 Renderer 全局状态。
- Capture 数据库与 `diagnostics.sqlite` 使用独立 Writer；日志 Sink 失败不能阻塞或回滚 Capture 写入。
- Diagnostics 只保存脱敏结构化 attributes，不保存完整 Command、Body、Authorization、Cookie、Token、CA 私钥或敏感 URL Query。
- 开始后按 Server/Contract/Client 分别记录进度；T2.0 记录设计截图对照、交互状态、可访问性和 packaged 视觉验证，存储任务记录 schema、migration、性能数据、验证和剩余工作。
