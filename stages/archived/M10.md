## 进入条件与记录规则

- 所有导入按不可信输入处理，限制路径、尺寸、数量和压缩比。
- Diagnostics 导出默认脱敏，不包含 Body、Authorization、Cookie、Token、CA 私钥或敏感 URL Query。
- Main/Renderer 日志汇入 Diagnostics 时复用 Core 的脱敏规则与有界策略；日志必须标注 process 来源，跨进程可按 trace/请求关联；Renderer 侧只经既有窄 IPC 通道上报，不放宽 Preload 面。
- 开始后按 Server/Contract/Client 分别记录进度，并记录格式版本、安全测试、兼容性、截图验证和剩余工作。

## T10.1 HAR 1.2 导入/导出（已完成）

### 实施

- **Core HAR 门面**：`proxy-core/har/entry.ts` 的 `HarService` 直接作为模块入口，组合 `HarJobManager`、`HarDocumentParser`、`interfaces/index.ts` 与 `utils/index.ts`。导出按 Storage keyset 页枚举 detail，正文只在 Core 从 Blob 分块读取，HAR entry 逐条写同目录临时文件后替换目标；导入先完成不可信 JSON/schema/数量/正文校验，再建立 `har-import` Session、分批写 Blob/Exchange，失败或取消按新 Session 回滚并 GC 孤立 Blob。
- **HAR 映射**：导出标准 `log.version=1.2`、creator、request/response/header/query/cookie 空数组/content/timings；Response 遇 gzip/deflate/br 时先按 `Content-Encoding` 解压，`bodySize` 保持线上编码大小，`content.size` 记录解码大小并填写 `compression`，避免兼容工具把压缩字节当正文。文本正文直接写 text，二进制用 base64（request 使用 `_encoding` 扩展，response 使用标准 `encoding`）。导入映射 HTTP/1.1/H2/H3、状态、header、MIME、时序与双向正文；捕获到的 `<script>` 只作为 inert 字节存储，代码中不存在 eval、DOM 注入、插件或脚本执行路径。
- **格式损失**：HAR 无法表达 HTTP/2 pseudo-header/trailer、WebSocket message、TLS detail 与 rule history；Core 完成结果与 UI 都显示警告。Native archive 显示 disabled，留 T10.2。
- **异步任务契约**：Core protocol 新增 `har.export.start`、`har.import.start`、`transfer.job.get/cancel` 与 `TransferJobSnapshot`；任务有界保留 100 项，使用专属 AbortController，公开快照只含 basename/进度/状态/警告，不返回绝对路径。Main 通过 Electron `showSaveDialog/showOpenDialog` 产生真实路径，Renderer 只提交 scope/redaction 并轮询 job，永不获得通用文件系统 API。
- **Renderer**：Capture Topbar 删除无行为的 Info/Settings/More，改为 `Import` / `Export` 两个文件菜单。Import 提供 `Import HAR` / `Open Capture`，Export 提供 `Export HAR` / `Save Capture`；四种命令进入各自单一动作弹层，不再把 HAR 与 Interceptor Capture 表现为同一 Format。Export HAR 支持 all/current filter/selected scope（current filter 会把 H1/H2/WS protocol group 一并下推）、Authorization/Cookie 遮罩和 strip bodies；其余动作只显示对应格式说明、敏感信息警告、进度、取消与错误。All traffic 数量来自 `storage.status`，分页 filter 不冒充已知总数。导入完成重新拉取 Capture 首页。业务 Renderer 无 fixture/DEV setter；visual parity 通过 fake Preload + 正常 UI 点击建立状态。
- **输入上限**：HAR 文件 256 MiB、100,000 entries、每 entry 1,000 headers、单 header value 8 KiB、URL 16 KiB、单 body 64 MiB；仅接受 `http/https/ws/wss` URL；base64 使用严格语法校验。Main/Core 两层 command 校验 scope、selected ID、filter、redaction、path 与 job ID。
- **Core 模块结构统一**：按仓库约定同步整理 composer/connection/diagnostics/grpc/har/proxy/rules/storage：根 Service/Engine 直接位于 `entry.ts`，显式类型集中 `interfaces/index.ts`，无状态函数集中 `utils/index.ts`，其余文件使用模块前缀且一文件一个 class；host/worker 子模块入口为 `entry.ts`、其余文件保持 `host-*`/`worker-*`。esbuild 与运行时 resolver 已同步输出 `storage/worker/entry.cjs`、`diagnostics/worker/entry.cjs`。

- 导入只用 `JSON.parse` 与结构化字段读取，未知扩展字段忽略；不加载远程资源、不渲染捕获 HTML、不执行脚本。

## T10.2 原生 archive（已完成）

### 实施

- **共享任务基础设施**：把原 HAR 专用 job manager 泛化为 `transfer/entry.ts` 的 `TransferJobManager`（通用 `start(jobId, kind, filePath, operation)` + get/cancel/cancelAll），CoreApplication 独占一个实例，`HarService` 与新 `ArchiveService` 共用；`transfer.job.get/cancel` 直接查询该实例。未新建第二套任务基础设施。
- **依赖零新增的 ZIP**：`archive/archive-zip-writer.ts` 手写流式 ZIP 写入（占位本地头 + 流式 `deflateRaw` + 回填 crc/大小 + central directory/EOCD，FileHandle 定位回填避免数据描述符），`archive/archive-zip-reader.ts` 手写读取。CRC-32、条目名安全、manifest 解析集中在 `archive/utils/index.ts`。全部用 Node `zlib`/`crypto`，`npm audit --omit=dev` 保持 0。
- **一致 SQLite 快照**：`storage` 新增 worker 请求 `snapshot` → `CaptureStore.snapshotInto` 用 `PRAGMA wal_checkpoint(TRUNCATE)` + `VACUUM INTO ?` 生成紧凑一致快照，不复制活动库文件。`StorageService` 新增 `snapshot`/`referencedBlobHashes`/`openBlobStream`（`BlobStore.openReadStream` 流式读引用 Blob）。
- **导出**：`ArchiveService.exportToFile` 生成 `capture.sqlite` 快照 → 逐个流式写入引用 Blob（`blobs/<sha256>`）→ 最后写 `manifest.json`（format/archiveVersion/schemaVersion/appVersion/createdAt + 每文件 path/size/sha256）→ `finalize` → 原子 rename；临时快照/临时 ZIP 在失败或取消时清理。
- **导入（不可信输入处理）**：先 stat 大小上限 → 解析 EOCD/central directory → **提取任何字节前**校验全部条目（拒绝加密位、非 store/deflate、符号链接、绝对/`..`/反斜杠/穿越、非白名单名、单条与总解压上限、压缩比 zip-bomb 上限、重复名）→ 提取并解析 manifest（拒绝未知 format/不支持版本/`schemaVersion > 当前`）→ manifest 与 central directory 交叉一致校验 → 提取快照与 Blob 到临时目录并逐文件校验 size+sha256 → 提取时按声明大小设硬上限并逐条校验 CRC-32 → Blob 经内容寻址 `writeBody` 导入并断言 hash 一致 → 快照 `PRAGMA integrity_check` → 用 storage 拥有的 `CaptureStore` 读快照，把 Exchange（含 pseudo-header/trailer/正文引用/WebSocket 帧）重插入隔离 Session；失败或取消回滚该 Session。
- **契约与桌面**：协议新增 `archive.export.start`/`archive.import.start`（payload `{jobId, filePath}`）与 `TransferJobKind` 的 `archive-export`/`archive-import`；窄 API 新增 `startArchiveExport`/`startArchiveImport`（Main 用 `showSaveDialog`/`showOpenDialog` 持有 `.iarchive` 路径）。Capture 把 archive 定位为 `Open Capture` / `Save Capture` 独立命令，不再与跨工具 HAR 共用 Format 切换；进度、取消与终态继续复用 transfer job 轮询。

### 安全与格式决策

- archive 为版本化容器：archive/schema/app 三个版本相互独立；导入只接受已知 `archiveVersion`，且 `schemaVersion` 不得高于当前 Capture schema（低版本经 `openCaptureDatabase` 只向前迁移）。
- 解压前完成全部安全校验，杜绝目录穿越、符号链接、加密条目、zip bomb（压缩比 + 单条/总解压绝对上限双护栏）；提取时以声明大小为硬上限并逐条 CRC-32 校验，Blob 再经内容寻址 hash 三重校验。
- 文件路径只存在于 Main→Core 内部 typed command 与临时目录，Renderer 与公开 job snapshot 不含绝对路径。ZIP 不支持 ZIP64（本产品写入器也不产生），遇到即拒绝。
