## 实施记录

### 关键决策

- **CA 管理归 Main，Core 只做 MITM**：Electron `safeStorage`（DPAPI/Keychain）只在 Main 可用，故 CA 生成/加密存储/信任库操作全在 Main；Core（Mockttp）经内部 `tls.configure` 命令接收解密后的 CA 做 MITM。私钥只在 Main→Core 内部 MessagePort 单向下发，暴露面最小。这是相对产品设计图（Cert Service 画在 Core）的务实偏离，动机同 M3 采用 Mockttp。
- **Main 不依赖 mockttp 生成 CA**：mockttp 含原生/WASM 不宜进 Main bundle；改用纯 JS 的 `@peculiar/x509`（mockttp 同款）生成 CA。
- **证书库懒加载（重要）**：`@peculiar/x509` 依赖 tsyringe（需 reflect-metadata polyfill），在 Main bundle 顶层 import 会阻塞 Chromium/CDP 启动（packaged smoke 报 “CDP endpoint did not start”，且 Main 不退出、stderr 空，极难诊断）。故 `CertificateService` 顶层不 import 证书库，`generate()` 内 `await import('reflect-metadata')` + `await import('@peculiar/x509')` + `cryptoProvider.set(webcrypto)`（缓存）；Main 启动路径完全不碰证书库。
- **信任后才 MITM**：`provisionCoreTls` 仅当 CA 已安装信任（`trustStore.isTrusted`）时才下发 CA material 启用 MITM，否则下发 null（CONNECT 直通不解密），精确对应“CA 受信任后才启用 TLS MITM”。
- **不放无后端死控件**：证书面板去掉设计稿中暂无后端的 Export、System-store（机器级需提权）控件，保留真实可用功能；后续里程碑再补。

## 后续增强（2026-07-15：CA 可用性与信任模型）

M5 收官后按真实使用反馈做的增强，不改变「私钥不出 Main / 信任后才 MITM」核心边界：

- **信任库从 current-user 改为 local-machine（需管理员提权）**：`TrustStoreService` 用 `@vscode/sudo-prompt` 提权执行 `certutil -addstore -f Root`（Windows，去 `-user`）/ `security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain`（macOS）；检测走非提权 `certutil -verifystore Root <sha1>` / `security find-certificate`。注入 `ElevatedRunner`（默认 `sudoPromptRunner`）与 `systemKeychainPath` 便于 mock 单测。动机：本机全部用户/进程（含浏览器）统一信任，消除 current-user 与 local-machine 混淆。
- **MITM 与信任解耦**：新增独立 `mitmEnabled` 开关（Settings「Decrypt HTTPS」），与 CA 是否受信任解耦；`provisionCoreTls` 仅当 `trusted && mitmEnabled` 才下发 CA material。窄 API 加 `setHttpsDecryption(enabled)`。
- **Install 不自动生成**：`ca:install` 去掉 `service.ensure()`，改为检查 `getStatus().present`，未生成即报错；UI 未生成时禁用 Install 并提示「需先生成 CA」——生成是用户显式独立操作。
- **证书管理入口**：新增 `ca:reveal`（文件管理器定位 CA）、`ca:view`（导出 DER `.cer` 后 `shell.openPath` 看系统证书详情）、`ca:open-manager`（Windows `certmgr.msc` / macOS Keychain Access）、`ca:delete`（先移除信任再删文件；trusted 时禁用 Regenerate/Delete）。窄 API：`revealCertificate`/`viewCertificate`/`openCertificateManager`/`deleteCertificate`；`CertificateInfo` 增 `path`/`mitmEnabled`。
- **打包修复**：Electron Vite 用 rolldown 打包 `@peculiar/x509`（tslib interop）触发 `__extends` 崩溃，故 `vite.main.config.ts` 将 `@peculiar/x509`/`reflect-metadata`/`@vscode/sudo-prompt` 标为 `rollupOptions.external`。**external 模块的顶层 require 会阻塞 packaged Main/CDP 启动**（同 M5 x509 踩过的坑），故 `@vscode/sudo-prompt` 与 `@peculiar/x509` 均懒加载（用时 `await import`，Main 启动路径不碰）；packaged smoke 验证 CDP 与 Preload 面正常。
- **UI 无闪烁**：证书面板改用 IPC 返回值直接 `setState`（`applyInfo`/`applyHosts`），不再整面板 reload；Trust 状态标签改「Local machine · 本机全部用户 · 安装/移除需管理员提权」。

代码：`certificates/trust-store-service.ts`（`ElevatedRunner`/`sudoPromptRunner`/local-machine 命令）、`certificate-service.ts`（`delete()`/`getCertificatePath()`）、`main.ts`（`ca:reveal/view/open-manager/delete`、`https:set-decryption`、`mitmEnabled`、install 不自动生成）、`shared/desktop-api.ts`、`preload/preload.ts`、`features/settings/SettingsContent`、`vite.main.config.ts`、`tests/packaged-smoke/startup.spec.ts`（apiKeys）。依赖新增 `@vscode/sudo-prompt`。

## 后续增强（2026-07-18：默认直通与按需 HTTPS Setup）

- Main 每次启动都以 `mitmEnabled=false` 开始，不因磁盘上已有 CA 或信任状态自动解密 HTTPS，也不在应用启动时生成或安装证书。
- Core 未收到 CA material 时用 `tlsInterceptOnly: []` 明确让所有 TLS 走 passthrough；仅记录 CONNECT 目标 host/port、开始/结束和 duration，不保存隧道内 header/body，也不伪造 TLS 版本、证书链或 Connection 外键。
- 未解密隧道在 Capture 中显示为 `CONNECT` / `tls` / `application/x-encrypted-tunnel`，Inspector 使用单独 Tunnel 面板解释“流量已路由但内容未解密”。
- 用户从 Tunnel 面板显式打开 HTTPS Setup，按需执行 Generate CA、Install trust 和 Start decrypting；只有用户完成授权并点击启用后，Main 才向 Core 下发私钥 material 并重启 listener 进入 MITM。
- Cookies、Timing 和 Payload 等明文 Inspector 能力只对已解密 Exchange 展示；默认直通路径仍可观察目标、状态与隧道时长。
