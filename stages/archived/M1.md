## 阶段目标

在 Electron Main 与其管理的 Proxy Core UtilityProcess 之间建立类型化、可取消、可诊断的 RPC 通道，并通过窄 Preload API 验证 Renderer → Main → Core 往返。

M1 不实现 HTTP 代理、存储、真实 Traffic Event 或业务规则。

## 最终设计

```text
Renderer -> Preload -> DesktopApplication -> CoreRuntime
                                          |-- UtilityProcess / heartbeat / restart
                                          `-- CoreRpcClient
                                                 <MessagePort>
CoreProcess -> CoreApplication ----------- CoreRpcServer
                  `-- CoreDiagnostics      校验/correlation/cancel
```

### 为什么保留 heartbeat

- `ready` 和 CoreProcess `exit` 只能发现启动与退出，无法发现“CoreProcess 仍存在，但 Node Event Loop 已卡死”。
- CoreProcess 每秒通过生命周期 `parentPort` 发送 heartbeat；Main 4 秒未收到时将 CoreProcess 标记为 `unresponsive`、kill，并走退避重启。
- Renderer 看到的 `CoreProcessStatus.running` 仅表示最近收到 heartbeat，不代表 HTTP Listener、数据库等业务一定健康。
- 业务成功或失败由每个 RPC 的 Success/Error Response 表达，不再建立第二套 `core.health` command、Health subscription 或主动 health-check。

### 为什么使用 MessagePort

- Core 仅由 Main 启动，且与 Desktop 同包发布，不需要本地 Server、端口、Token 或跨版本协商。
- `parentPort` 只负责 ready、heartbeat、RPC port transfer、shutdown 和 stopped；业务 RPC 只走转交后的 MessagePort。
- 每条 Request 自带 `protocolVersion`、`requestId` 和 `traceId`，足以完成版本错配检测、Promise correlation 和日志关联。

### 为什么不在 M1 实现事件背压

- M1 的 Health Event/EventBatchQueue 仅服务于 smoke，没有真实产品消费者，属于提前设计。
- Capture Event 的字段、频率、最终态和可合并态只有在 M3/T3.2 的 Exchange 模型落地后才能可靠定义。
- 批处理、合并、sequence/ack 和慢消费者策略移动到 M3/T3.4，与真实 Capture workload 一起实现和压测。

## 已实现模块

- `packages/core-protocol/src/messages.ts`：传输无关的 typed command/result 和 RPC envelope。
- `packages/core-protocol/src/validation.ts`：拒绝未知字段、版本错配、非法 ID、分页/range/日志边界。
- `apps/desktop/src/main/main.ts`：`DesktopApplication` 统一拥有窗口、安全策略、IPC 和一个 `CoreRuntime`。
- `apps/desktop/src/main/core/core-runtime.ts`：Main 的唯一 Core 入口；集中拥有 CoreProcess、heartbeat/restart/shutdown、MessageChannel 和内部 RPC client。
- `apps/desktop/src/main/core/core-rpc-client.ts`：CoreRuntime 内部的 typed RPC 状态机；负责 timeout/cancel/correlation/disconnect。
- `apps/desktop/src/main/utils/renderer-utils.ts`：Renderer IPC 输入校验和 Diagnostics DTO 映射纯函数。
- `apps/proxy-core/src/proxy-core/entry.cts`：最小可执行入口；只解析 UtilityProcess parentPort 并启动 CoreApplication。
- `apps/proxy-core/src/proxy-core/core-application.ts`：Core 子进程根对象；统一拥有 ready/heartbeat/shutdown/signal、RpcServer、Diagnostics 和后续 Storage/Proxy Service。
- `apps/proxy-core/src/proxy-core/core-rpc-server.ts`：只负责消息校验、request/cancel、response 和连接 replacement。
- `apps/proxy-core/src/proxy-core/core-diagnostics.ts`：结构化 Trace、Action 计时、三重上限、敏感 attribute 脱敏和 sink fallback。
- `apps/desktop/src/shared/desktop-api.ts`：只暴露 CoreProcess 状态、M1 echo 和脱敏 Trace，不泄漏通用 IPC 或 MessagePort。

## 必须保持的边界

- 不把业务 command 塞回 `UtilityProcess.parentPort`。
- 不把 `CoreProcessStatus.running` 描述为业务健康。
- 不增加通用 `send/invoke` 逃生口；Renderer API 必须继续面向意图。
- Main 不搬运未来请求/响应正文；Body 只走有限 range/chunk。
- CoreDiagnostics 不记录 Body、Authorization、Cookie、Token、CA 私钥或敏感 Query。
- 真实 Capture Event 与背压只在 M3/T3.4 实现。

## 已知后续工作

- M1 Diagnostics 只保存在内存 Ring Buffer；M2/T2.5 实现 Diagnostics Worker 与独立 `diagnostics.sqlite`。

- Core 当前无外部接入或跨语言编码层；约束改变时再增加 Transport Adapter。
