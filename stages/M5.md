## 实施记录

### 关键决策

- **CA 管理归 Main，Core 只做 MITM**：Electron `safeStorage`（DPAPI/Keychain）只在 Main 可用，故 CA 生成/加密存储/信任库操作全在 Main；Core（Mockttp）经内部 `tls.configure` 命令接收解密后的 CA 做 MITM。私钥只在 Main→Core 内部 MessagePort 单向下发，暴露面最小。这是相对产品设计图（Cert Service 画在 Core）的务实偏离，动机同 M3 采用 Mockttp。
- **Main 不依赖 mockttp 生成 CA**：mockttp 含原生/WASM 不宜进 Main bundle；改用纯 JS 的 `@peculiar/x509`（mockttp 同款）生成 CA。
- **证书库懒加载（重要）**：`@peculiar/x509` 依赖 tsyringe（需 reflect-metadata polyfill），在 Main bundle 顶层 import 会阻塞 Chromium/CDP 启动（packaged smoke 报 “CDP endpoint did not start”，且 Main 不退出、stderr 空，极难诊断）。故 `CertificateService` 顶层不 import 证书库，`generate()` 内 `await import('reflect-metadata')` + `await import('@peculiar/x509')` + `cryptoProvider.set(webcrypto)`（缓存）；Main 启动路径完全不碰证书库。
- **信任后才 MITM**：`provisionCoreTls` 仅当 CA 已安装信任（`trustStore.isTrusted`）时才下发 CA material 启用 MITM，否则下发 null（CONNECT 直通不解密），精确对应“CA 受信任后才启用 TLS MITM”。
- **不放无后端死控件**：证书面板去掉设计稿中暂无后端的 Export、System-store（机器级需提权）控件，保留真实可用功能；后续里程碑再补。
