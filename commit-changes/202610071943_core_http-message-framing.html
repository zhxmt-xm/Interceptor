HTTP编辑正文framing

2026-10-07 19:43

统一Breakpoint、Rule与Composer的replacement正文构造，修复chunked被改写为Content-Length及response CL/TE冲突。

Core

统一replacement content bytes

位置：apps/proxy-core/src/proxy-core/http-message/、proxy/与composer/。

改前：Breakpoint与Rule把Text/File直接交给Mockttp编码，Composer固定使用UTF-8；多层Content-Encoding失败，Capture Final可能不是实际wire bytes。

改后：HttpMessageService按最终charset生成Text bytes、保持File bytes，再依声明顺序执行多层Content-Encoding。代理链只在原消息存在且用户未编辑Content-Length时更新长度；Composer复用相同content构造。

原因与影响：Content-Encoding属于正文转换，由Core统一负责；Content-Length在content coding后计算。用户显式设置或删除CL时仍保留用户意图。

发送层只负责transfer framing

位置：patches/mockttp+4.5.0.patch。

改前：headers-stage body override再次编码正文并无条件写Content-Length，导致H1 chunked request丢失Transfer-Encoding，response同时出现CL/TE并被Node拒绝。

改后：hook接收Core已完成content coding的rawBody，只替换stream并排空原正文。Request通过write()后end()发送，避免end(buffer)绕过最终framing headers自动选择CL。

原因与影响：Transfer-Encoding、H1 chunk framing及H2 DATA frame继续由Mockttp/Node执行；patch不再承担产品header决策。

工程与文档

依赖、测试与契约同步

改前：charset和多层content coding依赖Mockttp传递实现，wire覆盖仅有两条失败的H1 chunked用例。

改后：Proxy Core直接声明iconv-lite与http-encoding；测试覆盖H1/H2 request/response、Text/File、header-only/body-only/header+body、CL继承/设置/删除、chunked及Capture Final bytes。真实Breakpoint workflow新增继承chunked段。

原因与影响：依赖与能力边界显式化，HTTP编辑契约、E2E规格和Handover保持一致。
