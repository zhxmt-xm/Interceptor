工程与文档 · ClashX恢复流程

  • 位置：E2E原生菜单driver fixtures/ui/macos-clashx.ts。改前把菜单勾选视为ClashX已经接管系统代理；改后读取全部network service，精确比较本轮ClashX的HTTP/HTTPS端口，并确认该端口由原ClashX进程监听。Interceptor接管后菜单仍勾选时，不再误判为ClashX持有代理。
  • 位置：workflows/settings/macos-upstream-proxy.workflow.ts的外部改写流程。改前先尝试停用ClashX；改后先通过真实菜单重新接管，再停用并关闭Interceptor，避免将“重新应用外部代理”误当成“停用”。
  • 位置：同一workflow新增的外部改写后崩溃重启流程。改前只覆盖外部改写后正常退出及未改写时的跨profile恢复；改后覆盖App A接管、ClashX外部改写、A崩溃、全新profile B启动和退出，逐项比较完整original/owned/effectiveProxies。
  • 位置：新增流程的清理顺序。先确认B退出后仍保留外部新配置，再通过ClashX真实菜单恢复workflow基线，最后执行原host guard；不放宽完整代理、证书信任、journal或进程检查。

原生操作通过System Events定位真实菜单项、读取菜单实际展开状态，再发送CoreGraphics鼠标移动和点击事件。打开、可见检查、点击及关闭确认在同一调用中完成，随后独立回读系统代理；不直接写系统代理，不调用产品业务API代替UI，不给产品增加测试参数。

文档

Settings明确完整快照比较包含service集合本身，不只比较仍存在的service；文件与状态机测试负责数据边界，ClashX真实用户流程负责系统代理接管、外部改写及退出恢复。

Settings workflow规格补充外部改写后的崩溃重启步骤，明确ClashX菜单状态、实际代理接管状态和最终宿主恢复是三个不同的观察点。本报告仅说明改动，验证证据与剩余范围由Handover和Settings功能文档维护。
